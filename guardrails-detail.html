The mechanisms behind each phase

Four phases, in the order they have to happen — what "good" actually looks like for each one, the real controls that get you there, and a question worth asking yourself before you claim you're covered.

PHASE 01 · DISCOVER

You can't govern what you can't see

What good looks like

A full, continuously updated inventory of every AI tool, agent and identity touching company data — sanctioned or not — and exactly what data each one can reach.

How it actually works
SaaS & API discoveryCASB / SSE

Sweeping OAuth grants, browser-extension telemetry and API gateway logs to surface every AI tool with a live connection into the environment — not just the ones procurement approved.

Data-flow mappingDSPM

Classifying where sensitive data actually lives, then tracing which of the discovered AI tools and agents can reach it — turning "we have 40 AI tools" into "we have 6 touching regulated data."

Non-human identity inventoryIGA

Every AI agent is a service account or API credential. Discovery has to treat it as an identity, not just an app — pulling from the identity provider, CI/CD and cloud IAM logs to catch agents provisioned outside a formal request.

Shadow AI scoringRisk scoring

A lightweight risk score per discovered tool — data sensitivity reachable, user count, governance status — so security isn't triaging 200 tools with the same urgency.

Why this comes first

It doesn't depend on anything — it's the floor everything else stands on. If Discover misses an agent, every later phase is blind to it too. It comes first because it's foundational, not because it's the most exciting problem to solve.

Ask yourself

If asked right now, could you produce a list of every AI agent with standing access to production data — not procured tools, agents — in under an hour?

PHASE 02 · CONTAIN

Discovery alone stops nothing in the moment

What good looks like

Real-time intervention on risky AI data flows as they happen — not a quarterly policy review that catches it three months later.

How it actually works
Inline data loss preventionDLP

Recognizing when sensitive content — a contract, source code, PII — is about to be pasted into or uploaded to a generative AI tool, and blocking or redacting it in the moment, not after the fact.

Policy-based routingCASB / SSE

Steering traffic to sanctioned AI tools with visibility, and blocking or warning on unsanctioned ones — applied consistently at the network and browser layer, not just at the edge.

Just-in-time, scoped accessCIEM

Instead of granting an agent standing read access to a dataset, granting scoped, time-bound access only for the specific task — so a compromised agent's blast radius is what it was doing, not everything it could theoretically reach.

Human-in-the-loop gatesWorkflow control

For actions above a risk threshold — bulk export, cross-system write, financial transaction — an approval step so agentic speed doesn't outrun oversight on the highest-stakes actions.

Why this depends on Discover

Containment policy is only as good as the inventory behind it — you can't set a control on a tool or data flow you don't know exists yet. This phase is what converts visibility into an actual brake pedal.

Ask yourself

Right now, if an employee pasted a client contract into an ungoverned AI tool, would anything actually stop it — or would you just find out later in a log?

PHASE 03 · GOVERN IDENTITY

Every AI agent is an identity

What good looks like

Every AI agent treated as a first-class, monitored identity — least-privilege, time-bound and behaviorally watched — the same rigor applied to a human privileged user.

How it actually works
Least-privilege by defaultCIEM

Provisioning agents with only the scopes their specific task needs — not a broad standing credential granted "to make setup easier" and never revisited.

Credential lifecycle managementPAM

Short-lived, automatically rotated tokens instead of static API keys that sit unreviewed for months — so a leaked or manipulated credential has a short shelf life.

Behavioral baseliningITDR / UEBA

Learning what "normal" looks like for a given agent — call volume, systems touched, time of day — and flagging deviations, the same way you'd flag a human account logging in from a new country at 3am.

Segmentation by boundaryIGA

An agent serving one region or one system shouldn't have a credential that also reaches three others "because it was the same service account." Identity boundaries should match business boundaries, not engineering shortcuts.

Why this depends on Contain

Containment stops the obvious, in-the-moment leaks. But a well-behaved agent with over-broad standing access is still a latent risk sitting quietly until something manipulates it. Identity governance closes that gap — it's the slowest phase to build, and the one most organizations are least mature in, which is exactly why it's the pivot point of the whole journey.

Ask yourself

Do any of your AI agents currently hold standing credentials broader than what they use day-to-day — and would you know if one of them started using the rest of that access?

PHASE 04 · INSTITUTIONALIZE

Tools alone don't hold this together

What good looks like

AI risk owned as a standing accountability, with real cadence and process — not a one-time project that quietly decays six months after the initial rollout.

How it actually works
Named ownershipGovernance

A specific role or team — not "everyone's responsibility," which usually means no one's — accountable for AI risk posture, reporting on it the way a CISO reports on general security posture.

A real intake pathProcess

A written, fast, sanctioned route for a team to request a new AI tool or agent — so the alternative to "wait weeks for approval" isn't "just use it without asking."

Recurring identity reviewsIGA

Scheduled access reviews for agents and their credentials, the same way privileged human accounts get periodically re-certified — not a one-time grant that's never revisited.

Metrics that travel upwardReporting

Coverage (% of AI tools and agents discovered and governed), exposure trend, and time-to-detect for AI-related anomalies — reported on a cadence a board or exec team actually sees.

Why this depends on the first three

Process without visibility, containment or identity controls is just a policy document. But tooling without process decays — new agents get provisioned outside the pattern the moment nobody's explicitly responsible for catching them. Institutionalizing is what keeps the first three phases from being a one-time clean-up.

Ask yourself

If a new AI agent went live in your organization tomorrow outside of IT, is there an actual process that would catch it — or would it depend on someone happening to notice?
